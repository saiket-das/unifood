# UniFood — Project Rules

These rules are mandatory for everyone who changes this repository: human
developers and every AI coding agent (Claude Code, Codex, Cursor, Copilot, local
agents and any other tool). They apply to every part of the monorepo.

This file is the single source of truth. `CLAUDE.md` imports it; do not copy
rules into other agent files. Specs live in `docs/` (APP_FLOW, PLAN, PRD,
SCHEMA, TRD). Where a rule below conflicts with an example in the docs, this
file wins.

---

## 1. Repository structure — every file has one correct home

### 1.1 Before creating any file or folder

1. Find where it belongs in the maps below.
2. If an existing file, module or feature folder already covers it, extend that
   instead of creating a parallel one.
3. If no location in this file fits, **do not invent one.** Agents must stop and
   ask the user. If a new location is approved, update this file and
   `scripts/check-structure.mjs` in the same change.
4. Run `pnpm check:structure` before committing. It fails on files in places
   this file does not allow.

### 1.2 Root — nothing else belongs here

| Entry                                                     | Purpose                                                  |
| --------------------------------------------------------- | -------------------------------------------------------- |
| `apps/`                                                   | The four applications (§1.3)                             |
| `packages/`                                               | Code shared by two or more apps (§1.4)                   |
| `infra/`                                                  | Local services, container builds, deployment (§1.5)      |
| `scripts/`                                                | Repository-wide developer scripts (§1.5)                 |
| `docs/`                                                   | Product and technical specifications (§1.5)              |
| `.github/`                                                | GitHub configuration and `SECURITY.md`                   |
| `AGENTS.md`, `CLAUDE.md`, `README.md`                     | Project rules, Claude import of the rules, setup guide   |
| `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`   | Workspace definition, shared versions, the only lockfile |
| `eslint.config.mjs`, `.prettierrc`, `.prettierignore`     | Lint and format configuration (tools require the root)   |
| `.editorconfig`, `.gitattributes`, `.gitignore`, `.nvmrc` | Editor, line-ending, ignore and Node version settings    |

A new root entry is allowed only when a tool cannot read its file from anywhere
else, and only with user approval.

### 1.3 `apps/` — exactly four applications

| App                   | What it is                                             |
| --------------------- | ------------------------------------------------------ |
| `apps/backend`        | NestJS API and background worker (two entrypoints)     |
| `apps/student-app`    | Next.js PWA for students                               |
| `apps/restaurant-pos` | Next.js owner dashboard, staff POS and kitchen display |
| `apps/admin`          | Next.js platform administration                        |

- Do not add another app, and never create a second folder for an existing app
  (no `api/`, `worker/`, `student/`, `admin-dashboard/`).
- An app never imports from another app. Shared code moves to `packages/`.
- Each app owns its `package.json`, `tsconfig.json`, `.env.example`,
  `README.md` and framework config. Nothing else sits at the app root.

**`apps/backend` layout**

```text
apps/backend/
  src/
    main.ts               API entrypoint
    worker.ts             Background worker entrypoint (BullMQ processors)
    app.module.ts         Root module
    modules/<module>/     One folder per domain module (see below)
      <module>.module.ts
      <module>.controller.ts
      <module>.service.ts
      <module>.processor.ts   Queue processor, if the module has jobs
      dto/                    Request and response DTOs
      <module>.service.spec.ts
    common/               Cross-cutting code only
      filters/            Global exception filter (§3)
      interceptors/       Response envelope interceptor (§2)
      guards/             Auth and permission guards (§4)
      decorators/         e.g. @RequirePermissions
      pipes/
      errors/             Central error-code registry (§3)
    config/               Typed configuration loaded from the environment
    database/             Prisma service and database helpers
  prisma/
    schema.prisma
    migrations/           Generated by Prisma; never edited by hand
    seed.ts               Local and dev seed data only
  test/                   End-to-end tests
```

- Domain modules are the ones listed in TRD §5, in kebab-case folders:
  `auth`, `users`, `access-control`, `restaurants`, `staff`, `menus`,
  `pricing`, `pos`, `tables`, `dining-sessions`, `orders`, `kitchen`,
  `billing`, `payments`, `shifts`, `delivery`, `telegram`, `recommendations`,
  `notifications`, `analytics`, `admin`, `audit`. A new module needs user
  approval and an update to TRD §5.
- A module uses another module only through its exported service, never
  through that module's Prisma queries or internal files.
- Domain logic never goes in `common/`. `common/` holds only code every module
  uses.

**Web app layout (`student-app`, `restaurant-pos`, `admin`)**

```text
apps/<web-app>/
  public/                 Static assets (icons, manifest)
  src/
    app/                  Next.js routes only: page, layout, loading, error
    features/<feature>/   Everything for one feature (cart, orders, menu, tables…)
      components/
      hooks/
      api.ts              Calls through the shared API client
      types.ts
    components/           App-wide components that belong to no single feature
    lib/                  API client setup, helpers, config reading
    styles/
```

- Route files in `src/app/` stay thin: they compose components from
  `features/`.
- Code starts inside its feature. It moves to `src/components/` only when a
  second feature in the same app needs it, and to `packages/ui` only when a
  second app needs it.

### 1.4 `packages/` — shared code only

| Package                 | Holds                                                       | Used by        |
| ----------------------- | ----------------------------------------------------------- | -------------- |
| `packages/contracts`    | API request/response types, including `ApiResponse<T>` (§2) | All apps       |
| `packages/shared-types` | Domain types and enums (order, payment, delivery statuses)  | All apps       |
| `packages/validation`   | Zod schemas shared by frontend forms and the backend        | All apps       |
| `packages/ui`           | React components shared by the three web apps               | Web apps only  |
| `packages/config`       | Tooling presets only (TypeScript); no runtime code          | All workspaces |

- Code moves into a package only when **two or more apps** need it. Code used
  by one app stays in that app.
- Dependency direction is one way: apps → packages. A package never imports an
  app. The backend never imports `packages/ui`.
- Do not add a new package without user approval.

### 1.5 `infra/`, `scripts/`, `docs/`, `.github/`

| Location            | Holds                                                              |
| ------------------- | ------------------------------------------------------------------ |
| `infra/docker/`     | `compose.yml` for local Postgres and Redis; production Dockerfiles |
| `infra/deployment/` | Hosting, CI/CD and environment configuration                       |
| `scripts/`          | Repository-wide setup and check scripts (`.mjs`), flat folder      |
| `docs/`             | Specifications only, numbered `NN_NAME.md`                         |
| `.github/`          | `SECURITY.md`, workflows and other GitHub configuration            |

A script used by only one app belongs in that app's `package.json` scripts or
folder, not in `scripts/`.

### 1.6 Environment files

Each location that needs settings has its own ignored `.env` and a committed
`.env.example` beside it: `infra/docker/`, `apps/backend/`,
`apps/student-app/`, `apps/restaurant-pos/`, `apps/admin/`. There is no root
`.env`. Backend secrets live only in `apps/backend/.env`. Web apps hold only
their port and `NEXT_PUBLIC_*` values. When you add a key, add it to the
matching `.env.example`.

### 1.7 Naming

- Folders: kebab-case (`dining-sessions`, `order-card`). Next.js routing
  folders (`(group)`, `[id]`, `@slot`, `_private`) are the exception.
- TypeScript files: kebab-case with dot-suffixes for their role:
  `orders.service.ts`, `create-order.dto.ts`, `order-card.tsx`,
  `use-cart.ts`, `orders.service.spec.ts`.
- Exported React components and classes use PascalCase names inside the file.
- Tests sit next to the code they test (`*.spec.ts`, `*.test.tsx`), except
  backend end-to-end tests in `apps/backend/test/`.

### 1.8 Never create

- Any root file or folder not listed in §1.2.
- Copies or alternate versions: `orders2.ts`, `new-orders.ts`, `*.old`,
  `*.bak`, `*.orig`, `* copy*`, `final-*`.
- Scratch or experiment files in the repository: `test.ts`, `temp/`, `tmp/`,
  `playground/`, `scratch/`. Agents keep scratch work in their own temporary
  directory outside the repository.
- A second lockfile or package manager file (`package-lock.json`,
  `yarn.lock`, nested `pnpm-workspace.yaml`).
- Generic dumping grounds: `misc/`, `helpers/` or `utils/` at an app root.
  Name helpers after what they do and place them in the owning feature or
  module.
- Empty folders, except a `.gitkeep` in a location this file names.
- READMEs in subfolders. Only the repository, each app and `packages/` have one.
- Build output, generated clients, `.env` files or OS files such as
  `.DS_Store`.

## 2. API success response — always the same envelope

Every successful backend response uses this exact shape. No endpoint returns a bare
object, array, or string.

```json
{
  "success": true,
  "statusCode": 200,
  "message": "Order created successfully",
  "data": {},
  "meta": {
    "requestId": "uuid",
    "timestamp": "2026-11-22T10:00:00.000Z",
    "pagination": { "page": 1, "limit": 20, "total": 134, "totalPages": 7 }
  }
}
```

- `statusCode` always matches the real HTTP status (200, 201, …). Don't use 204; return
  200 with `data: null` so every response has a body.
- `message` is human-readable and safe to show to users.
- `data` is the payload (`null` when there is none).
- `meta.pagination` is present only on paginated collections.
- **Backend:** build responses in one place only (a global interceptor + a shared
  `sendResponse` helper). Controllers never hand-craft the envelope.
- **Shared type:** define `ApiResponse<T>` once in `packages/` and use it in every app.

## 3. API error response — always the same envelope

Every error (validation, auth, not found, business rule, unexpected) uses this shape:

```json
{
  "success": false,
  "statusCode": 422,
  "message": "The selected item is no longer available.",
  "error": {
    "code": "ORDER_ITEM_UNAVAILABLE",
    "details": [
      { "field": "items[0].menuItemId", "message": "Item is out of stock" }
    ]
  },
  "meta": {
    "requestId": "uuid",
    "timestamp": "2026-11-22T10:00:00.000Z"
  }
}
```

- `error.code` is a stable UPPER_SNAKE_CASE code from a central error-code registry.
  Frontends branch on `code`, never on `message` text.
- `error.details` is optional, used for field-level validation errors.
- **Backend:** one global exception filter converts every thrown error to this shape.
  Never expose stack traces, SQL/Prisma errors, or internal IDs to clients — log them
  server-side with the `requestId`.
- **Frontends:** one shared API client parses this envelope. Errors are shown to the
  user through one shared mechanism (e.g. a toast / form-error helper), always using
  `message`, with the same look across all apps. No per-page ad-hoc error handling.

## 4. Never hardcode actor roles

- Never assign, grant, or default a user's role in code (e.g. `role: 'OWNER'`,
  `isAdmin = true`, `if (email === ...)`). Roles come from the database
  (`platform_roles`, `user_platform_roles`, restaurant membership) via sign-up,
  invitation, or admin action.
- Authorization checks use **permissions** (e.g. `order.refund`, `menu.update`) resolved
  from the user's roles in the database — not `if (user.role === 'MANAGER')` scattered
  in code.
- Use guards/decorators (`@RequirePermissions(...)`) on the backend. Frontends only hide
  or show UI based on permissions returned by the API; the backend is always the
  source of truth.
- Seed data may create roles for local/dev setup only, never in application logic.

## 5. Never hardcode business rules

Values like prices, tax rates, service charges, delivery fees, order limits, opening
hours, cancellation windows, commission rates, timeouts, and status transitions must
not be literals in code.

- Store them in the database (restaurant settings, platform configuration) or in
  typed config loaded from environment variables.
- Put each rule's logic in one domain service, not duplicated across controllers or
  frontends.
- Frontends read these values from the API; they never re-implement or duplicate
  backend business rules (display-only formatting is fine).
- Secrets and environment-specific values live in `.env` (never committed);
  `.env.example` documents every key.

## 6. Verify every API before committing

Before committing any API change, verify and confirm each item:

- [ ] Success response matches the envelope in §2 (status code, message, data, meta).
- [ ] Every error path matches the envelope in §3 (validation, 401, 403, 404, 409, 422, 500).
- [ ] Input is validated with DTOs; unknown fields are rejected.
- [ ] Auth guard and permission checks are applied; tested with a user **without**
      permission (expect 403) and **without** a token (expect 401).
- [ ] Resource ownership / tenant scoping is enforced (one restaurant can never read or
      change another restaurant's data; IDOR checked).
- [ ] No sensitive data in responses (password hashes, tokens, internal fields).
- [ ] No SQL/NoSQL injection, mass assignment, or unbounded queries (pagination limits).
- [ ] Rate limiting / idempotency applied where the TRD requires it.
- [ ] No hardcoded roles or business rules (§4, §5).
- [ ] Lint, type-check, tests and `pnpm check:structure` pass.

If any item fails, fix it before committing. Do not commit "to fix later".

## 7. Git workflow

- **Never push directly to `main`.** All work goes to `dev` or a feature branch
  (`feat/...`, `fix/...`), and reaches `main` only through a pull request.
- Never force-push to `main` or `dev` without explicit approval, and always
  `git fetch` and check the remote first.
- Never add Claude/AI attribution (co-author trailers, "Generated with" lines, logos)
  to commits or PRs.
- Never commit `.env` files or secrets.
